# Autonomous Graph Theory Conjecture-Making Pipeline

Architecture
The pipeline is a four-stage linear flow with a feedback loop:
[DB: 50+ named + random graphs]
        │
        ▼
[Stage 1] Hypothesis Generation
  ├─ TxGraffitiGenerator: sweep all invariant pairs → fit linear inequalities → Dalmatian dominance filter
  └─ FunSearchGenerator: 2-round LLM evolution (seed prompt → elite re-prompt via Anthropic API)
        │
        ▼  ◄─────────────────────────────────────────────────┐
[Stage 2] Falsification Loop                                 │ counterexamples
  ├─ Z3Falsifier: SAT encoding of α/ω/χ/γ/ν as Bool vars     │ re-ingested into DB
  ├─ MCTSFalsifier: UCT bandit over edge-flip actions        │
  ├─ VNSFalsifier: k-edge shake + local search               │
  └─ CrossEntropyFalsifier: edge-probability evolution ───────┘
        │
        ▼
[Stage 3] Autoformalization
  └─ GraphOfThoughtFormalizer: 2-stage LLM (decompose → synthesise Lean 4) + optional lean binary check
        │
        ▼
[Stage 4] Theorem Proving
  └─ NeuralProverClient: LeanSubprocess → GoedelProver stub → DeepSeekProverV2 stub
        │
        ▼
  JSON report + plain-text summary
Central data object: Conjecture carries the informal statement, a structured Inequality, Lean 4 statement/proof, status, and the counterexample graph when falsified. Every stage mutates status in place.

## Refined Pipeline Description

### Stage 1 — Hypothesis Generation

**TxGraffiti-style generation** [mature research tool; open-source]:
The system evaluates a battery of numerical graph invariants (chromatic number χ, independence number α, clique number ω, domination number γ, matching number ν, max/min degree Δ/δ, etc.) and Boolean graph properties (bipartiteness, planarity, regularity) over a finite database of named and randomly constructed graphs. Candidate linear inequalities of the form `a·f(G) ≤ b·g(G) + c` are generated by exhaustively sweeping coefficient pairs and tightest-fitting offsets. The **Dalmatian heuristic** — a dominance filter — discards any conjecture subsumed by a strictly stronger one that also holds on the entire database: conjecture Q is eliminated if there exists Q′ such that Q′(G) ≤ Q(G) for all database graphs and Q′(G) < Q(G) for at least one. Only the Pareto-optimal frontier (tight on at least one graph, not dominated by any other surviving conjecture) is retained.

**FunSearch-style evolution** [research prototype; no public API]:
For extremal combinatorics and algorithmic graph constructions, the system uses a program-evolution loop inspired by DeepMind's FunSearch [1]. An LLM is prompted with the highest-scoring Python functions discovered so far (drawn from a scored *program database*) and asked to produce improved variants. Each candidate function is executed against the graph database by an automated evaluator that scores it according to how strongly its output correlates with or bounds existing invariants. Evolutionary selection pressure accumulates novel invariant relationships that are then converted into conjecture form. Note: the original FunSearch was demonstrated on the Cap Set problem and online bin-packing; graph-theoretic applications are an active research direction.

---

### Stage 2 — Iterative Falsification Loop

Generated conjectures are subjected to aggressive counterexample search via four complementary strategies:

- **Z3/SMT solvers** [production-ready]: graph structure is encoded as Boolean edge variables; invariant constraints (k-colorability, independence set size, etc.) are expressed as pseudo-Boolean and propositional formulae; Z3 searches for a satisfying assignment that violates the conjecture. Effective for small graphs (≤ 10 vertices) and invariants with compact SAT encodings.

- **Monte Carlo Tree Search (MCTS)** [standard AI technique]: a UCT-bandit search that builds a tree of graph modifications (edge additions/deletions), using rollout value = negative slack of the conjecture as the reward signal. Balances exploration of novel graph families with exploitation of promising structural regions.

- **Variable Neighborhood Search (VNS)** [well-established metaheuristic]: systematically cycles through increasingly large neighborhoods of the current best candidate (1-edge flip → k-edge flip → vertex rewiring), accepting any move that reduces the conjecture's slack. Restarts from a random graph when trapped in a local minimum.

- **Cross-entropy method** [probabilistic optimization; not reinforcement learning]: maintains a probability distribution p_e over each potential edge, samples graphs from this distribution, identifies the elite fraction (smallest slack), and updates p_e toward the empirical edge frequencies in those elite graphs. Converges toward graphs that most severely stress the conjecture.

Any counterexample found is immediately re-ingested into the hypothesis generation database, dynamically tightening subsequent conjectures.

---

### Stage 3 — Autoformalization

Conjectures that survive falsification are translated into machine-verifiable Lean 4 statements [research prototype]. The translation pipeline uses an LLM guided by a **Graph-of-Thought** decomposition: the informal statement is recursively broken into sub-goals (define the graph class, state the invariant bounds, quantify over all graphs), and each sub-goal is independently mapped to established definitions in Lean's `mathlib4`. The approach is inspired by the *Aria* autoformalization framework [2], which applies recursive semantic grounding to ensure every term in the formal statement corresponds to a `mathlib` definition. The generated Lean 4 code requires subsequent human or automated verification against the Lean type-checker kernel (which constitutes Lean's formal guarantee of correctness); the LLM output alone is not a proof.

> **Correction from original**: "strictly verified Lean 4 code" is imprecise. The *generated* Lean 4 code is a formal candidate; it is **type-checked** (kernel-verified) by the Lean elaborator only if it compiles successfully. The LLM's output may contain elaboration errors requiring manual repair.

---

### Stage 4 — Automated Theorem Proving

Type-checked Lean 4 statements are passed to neural theorem provers [cutting-edge research prototypes; no stable public API]:

- **Goedel-Prover** [2] — a frontier open-source automated theorem prover targeting Lean 4, demonstrating state-of-the-art performance on the miniF2F benchmark.
- **DeepSeek-Prover-V2** [3] — applies reinforcement learning with subgoal decomposition to produce complete, machine-checkable Lean 4 proofs.

Both systems require substantial GPU infrastructure and are accessed via research APIs (not publicly available as of 2025). The pipeline stubs these calls with a clean interface (`NeuralProverClient`) that documents the expected request/response schema.
